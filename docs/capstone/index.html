Content Performance Opportunity Scoring

A decision-support analysis for identifying content that may deserve search-visibility review, monitoring, or CTR/metadata review using observed search and engagement signals.

Author: Muhammad Faisal
Lane: Refresh / Content Opportunity Scoring

Abstract

This study asks whether observed search and engagement signals can be used to rank content items for editorial review and monitoring. Using 30,000 anonymized content items from the FlyRank ML Internship dataset, the analysis uses nine non-identifier features and a client-held-out evaluation design. A Logistic Regression model was compared with a transparent CTR-based baseline and evaluated using precision, recall, F1, and ROC-AUC. At a decision threshold of 0.10, the model achieved an F1 score of 0.2983 and recall of 0.9009, compared with an F1 score of 0.1703 and recall of 0.1535 for the baseline. The resulting ranking is intended as decision-support for prioritizing content review rather than as causal evidence or a claim about any search-engine ranking algorithm.

1. Problem Statement

Content teams often have many pages that could potentially be reviewed, but limited time to inspect every page individually. The practical question is therefore not simply whether a page performs well or poorly, but which pages should receive attention first.

Research question: Can observed search visibility, traffic, and engagement signals be used to rank content items for practical review and monitoring?

Decision supported

The output supports an editorial prioritization decision: which content items should be reviewed for search visibility, reviewed for CTR or metadata, or monitored.

Unit of analysis

The unit of analysis is an individual content item.

Human action

An editor or analyst can use the ranked output as a review queue, starting with higher-scored content and examining the associated reason code before deciding what action is appropriate.

Cost of a wrong call

A false positive can waste editorial time on a page that does not need attention. A false negative can cause a potentially useful review opportunity to be missed. Because of this trade-off, the model is used for prioritization rather than automatic publishing or deletion.

3. Methodology

Features

Nine numeric features were used as model inputs:

impressions_90d
clicks_90d
pageviews_90d
sessions_90d
avg_position
ctr
engagement_rate
scroll_rate
ai_traffic_pct

Target definition

The target was a binary performance_positive label, with the positive class containing 4,388 of the 30,000 content items.

Baseline

The baseline used a transparent CTR rule. It provided a simple, interpretable reference point against which the Logistic Regression model could be evaluated.

Validation design

The evaluation used a client-held-out split. The training data contained 23,837 rows from 25 clients, while the test data contained 6,163 rows from 7 clients.

Client overlap: 0. No clients were shared between the training and testing sets. This makes the evaluation more conservative than randomly mixing content from the same clients across both sets.

Decision threshold

The model's default threshold of 0.50 produced very few positive predictions. Threshold analysis showed a more useful operating point at 0.10, where recall increased substantially.

5. Limitations & Honest Framing

This work describes observed relationships in the available dataset. It does not establish causal relationships.

What the analysis can say

  • Observed signals were associated with the measured target.
  • The model can rank content items according to its learned score.
  • The output can support editorial prioritization.
  • The evaluation provides a directional comparison with a simple baseline.

What the analysis cannot say

  • It does not prove that changing a page will cause a ranking improvement.
  • It does not prove Google's ranking algorithm or any search-engine algorithm.
  • It does not establish that a recommended action will cause traffic growth.
  • It should not be interpreted as an automatic publish, rewrite, merge, or prune decision.
Important: The model has a modest ROC-AUC of 0.5914 and produces many false positives at the selected threshold. Therefore, the output should be treated as a prioritization and decision-support tool rather than a high-confidence classifier.

8. Reproducibility

The analysis was developed in Google Colab using Python, pandas, NumPy, scikit-learn, and Matplotlib.

Evaluation setup

  • Training set: 23,837 rows from 25 clients.
  • Testing set: 6,163 rows from 7 clients.
  • Client overlap: 0.
  • Model: Logistic Regression.
  • Final decision threshold: 0.10.
  • Leakage check: PASS.

Model inputs

The model used nine numeric features:

impressions_90d, clicks_90d, pageviews_90d, sessions_90d, avg_position, ctr, engagement_rate, scroll_rate, ai_traffic_pct

Excluded inputs

The model excluded content identifiers, client identifiers, the target, and trend-derived fields that could introduce leakage.

Randomness

No explicit random seed was recorded in the notebook. Therefore, this paper reports the results of the recorded run rather than claiming bit-for-bit reproducibility.

The complete capstone notebook and supporting work are maintained in the project repository.
